# Rust NTA 8800 service

## Collective gas heat-pump source draft

`POST /v1/nta8800/heat-pumps/gas-collective-source-draft/diagnose` and MCP tool `diagnose_gas_collective_source_draft` accept `{ "input": { "chain": { ... }, "sourceTemperatureClass": "below20_c", "sourceTemperatureReference": "...", "noQualityDeclarationConfirmed": true, "noQualityDeclarationReference": "..." } }`. The validated twelve-month linked gas chain is reused. Results keep collective source heat on the separate `dh` carrier and expose only draft fossil/renewable primary contributions from public consultation chapters 5 and 9. Invalid evidence returns HTTP 422 or an MCP tool error without partial numbers. Gas input, source pump/fan, final-edition verification, BENG and label are unavailable. See `docs/nta8800-gaswarmtepomp-collectieve-bron-concept.md`.

This service exposes the same `nta8800-core` crate used by the desktop app. A project with a complete `ntaCalculation` block can return BENG indicators and an indicative label class through the project-performance route; incomplete input returns explicit gaps. Results are unverified and unattested. The service does not register or issue an energy label.

## Run locally

From the repository root:

```bash
cargo run --manifest-path crates/nta8800-service/Cargo.toml --bin api
cargo run --manifest-path crates/nta8800-service/Cargo.toml --bin mcp
```

The API binds to `127.0.0.1:3007` by default. `OES_API_PORT` changes the port. It is intended for local development only.

The two generator-dispatch routes use `{ "input": { ... } }`. The first accepts twelve supplied `nodeInputKwh` records, `designContext: "new_build"`, and generator IDs, classes, rated thermal powers, efficiency values and evidence references. The second also requires matching forfait heat-pump input, a supplementary gas-boiler table input, source-system evidence and `declaredOperatingLimitsPresent`; optional `heatPumpAuxiliaryMeasurements` supplies only device identity and measurements. The kernel replaces any earlier standalone monthly auxiliary input with electricity derived in this dispatch chain; it returns no linked result when product-specific operating limits or a design supply temperature above 55 °C require a different dispatch route. MCP tools `diagnose_generator_dispatch_draft`, `diagnose_boiler_forfait_draft`, `diagnose_boiler_forfait_monthly_draft` and `diagnose_hybrid_heat_pump_monthly_draft`, plus matching Tauri commands, use the same Rust kernel. See `docs/nta8800-generatorverdeling-concept.md` for the consultation source and limits.

The `/validate` and `/calculate` POST body is `{ "project": { ... } }`, where `project` is the object inside an `.oes` file. Malformed project objects produce HTTP 400; structurally invalid input on `/calculate` produces HTTP 422. The JSON extractor may reject malformed request bodies before they reach the kernel. Validation checks positive zone/surface/window areas, parent references, construction references and windows that exceed their gross surface. Heating, ventilation, cooling and hot-water records must be objects with nonempty unique IDs and nonempty system types within each collection. The audit also checks recorded construction Rc/U and layer values, window U/g, thermal bridge length/Ψ and qv10 for basic physical validity. Missing legacy thermal properties are warnings; invalid supplied properties are errors. When every zone has complete surface/window geometry, `summary.envelopeGeometry` reports gross surface, window, and remaining opaque input areas per zone and in total. It is omitted if geometry is incomplete; these sums do not apply NTA transmission-area rules. The assessment also summarizes heat pumps and reports missing classification for legacy systems that have only a scalar performance value. A heating or hot water system may add `ntaHeatPump` with `id`, `source`, `sink`, `drive`, `reversible`, `hybrid`, `booster`, and `performanceEvidence`. The optional project-level `ntaHeatPumps` array stores additional classified assets without a legacy heating system type; each item may include `servedZoneIds`. The kernel checks IDs, zone references, evidence and useful sinks, and reports each standalone route as unimplemented. Classification does not enable a calculation route. Responses include `kernelVersion` and `inputFingerprint` (SHA-256 of the input JSON with object keys sorted) for traceability. The fingerprint identifies an input snapshot; it is not a calculation or attestation signature.

The reference audit POST body is `{ "case": { ... } }`; `case.project` is likewise the project object inside an `.oes` file. The response has an `inputFingerprint` for the project and a `manifestFingerprint` covering the whole case, including provenance, expected metrics and tolerances. The manifest schema and limits of the administrative audit are recorded in `docs/nta8800-referentieprotocol.md`.

The direct diagnostic comparison also accepts `{ "case": { ... } }`. Its case has `caseId`, `normVersion`, `source` (the same provenance fields as the reference audit), a typed direct-transmission `input`, and four `expected` metrics: `elementConductanceWPerK`, `linearBridgeConductanceWPerK`, `pointBridgeConductanceWPerK`, and `totalDirectConductanceWPerK`. Each expected metric has `path`, `value`, `unit: "W/K"`, nonnegative `absoluteTolerance`, and `calculationBasis`. An invalid case, including overflow of a finite absolute difference, returns HTTP 422 with no partial metrics; a valid comparison returns HTTP 200 with `compared_pass` or `compared_fail`, actual values, absolute differences, `inputFingerprint` and `caseFingerprint`. This compares submitted numbers only. It does not authenticate the stated publisher/reviewer or establish independence; `referenceVerified=false` and `bengCalculationAvailable=false` remain fixed.

The monthly direct diagnostic accepts `{ "input": { "direct": { ... }, "months": [ ... ] } }`. `direct` is the same explicit W/K input as `/transmission/direct/diagnose`. Supply exactly twelve unique `month` values 1–12 with `indoorTemperatureC`, `outdoorTemperatureC` and positive `hours`. The response gives each signed `H × (T_inside − T_outside) × hours / 1000` term in kWh and their annual signed sum; negative values are possible. An invalid or incomplete year returns HTTP 422 without energy values. Temperatures, hours and boundaries come from the caller: this does not apply an NTA climate, setpoint, utilization, ground, ventilation or demand method. See `docs/nta8800-maandtransmissie.md`.

The unheated-space diagnostic accepts `{ "input": { "spaces": [ ... ] } }`. Each named space supplies `reductionFactor` (0–1), `factorSourceReference` and an explicit `boundary` with the same A·U/L·Ψ/χ shape as the direct diagnostic. The response gives unreduced and reduced W/K per space and a sum; invalid input returns HTTP 422 with no partial values. This applies caller-supplied factors only. It does not derive the NTA factor or contribute to BENG. The MCP tool `diagnose_unheated_transmission` uses the same kernel. See `docs/nta8800-onverwarmde-transmissie.md`.

Surfaces, linear thermal bridges and point thermal bridges may include `thermalBoundary` with `outdoor`, `ground`, `unheated_space`, `adjacent_conditioned`, or `internal`. A zone may include `pointThermalBridges` with `id`, `name`, `chiValue` (W/K), `zoneId`, `thermalBoundary` and `sourceReference`. It must separately set `pointBridgeInventoryComplete=true` after the full point inventory is reviewed. `/validate` reports classification and inventory progress in `summary.thermalBoundaries`. Only when every surface and bridge is explicitly classified, linear and point lists are present, point inventories are confirmed, and the required outdoor geometry and U-values are usable does `summary.directOutdoorDiagnostic` contain a number. Its χ term includes only outdoor point bridges. It excludes ground, adjacent boundaries, corrections and BENG. Legacy files without boundaries or point-inventory confirmation remain readable and receive no derived number. Generated source references for surfaces and linear bridges point to project fields, not verified declarations; point references are supplied by the user and are not authenticated.

A project can include `unheatedSpaces` records with `id`, `name`, `reductionFactor` and `factorSourceReference`. Surfaces and bridges classified as `unheated_space` must refer to one of these records through `unheatedSpaceId`. `/validate` only emits `summary.unheatedTransmissionDiagnostic` when all boundaries and the point-bridge inventory are complete and the linked component values are usable. Invalid links or factors suppress the diagnostic.

Classified heat pumps may include `performancePoints` for measured or declared operating points. Each point requires a unique `id`, `service` (`space_heating`, `domestic_hot_water`, or `space_cooling`), `sourceTemperatureC` and `sinkTemperatureC` in °C, positive `usefulCapacityKw` and `inputPowerKw`, `inputEnergyCarrier` (`electricity`, `gas`, `district_heat`, or `other`), and a traceable `testReference`. The audit checks physical input limits, whether the service matches the sink and reversible flag, and that electric compression points use electricity as input. Two points with the same service, temperatures, useful capacity and carrier are rejected as ambiguous; a different useful capacity remains possible for future part-load modelling. For structurally valid input, `summary.performancePointDiagnostics` gives a finite `instantaneousUsefulToInputRatio` per point with pump ID, point ID, service and carrier. An overflowing ratio invalidates the input. This diagnostic ratio is neither a verified declaration nor annual COP/EER. `performanceEvidence` may also contain a `registryRecord` with `registrationNumber`, `productName`, `manufacturer` and `sourceUrl` for a controlled quality declaration. Old reference-only records remain readable with a missing-registry warning; incomplete supplied records are errors. The URL is only checked for HTTPS shape, not fetched or authenticated. Unknown fields inside `ntaHeatPump`, `ntaHeatPumps`, `performanceEvidence`, `performancePoints`, and `auxiliaryComponents` are rejected so misspelled performance data is not silently lost. No performance point or registry record is used for NTA interpolation, seasonal weighting, BENG, or label output yet.

Classified heat pumps with a DHW sink and controlled quality declaration may additionally store `dhwTestPoints`: unique tap profile, positive daily useful/input test energies (kWh/day), nominal capacity (kW), supplied practice factor, finite test/design setpoints (°C), optional source-air flow and dry/wet-bulb temperatures for exhaust-air products, declaration norm edition and source reference. `/validate` and MCP `validate_project` expose `summary.dhwTestDiagnostics` with the raw useful/input test ratio. This is not practice efficiency, annual performance, BENG or proof that an older declaration applies to the target edition. Three public two-profile input examples from BCRG 20240123GK, BCRG 20260044GK and BCRG 20260143GG (declaration norm editions 2020, 2024 and 2025) is documented in `docs/nta8800-tapwater-verklaringsinvoer.md`.

Classified heat pumps may also include `auxiliaryComponents`, each with a unique `id`, `kind` (`source_pump`, `source_fan`, `indoor_fan`, `distribution_pump`, `controls_standby`, `defrost`, `backup_heater`, or `other`), `service`, positive `nominalPowerW`, `energyCarrier`, `measurementBoundary` (`included_in_declared_performance`, `additional`, or `unknown`), and nonempty `evidenceReference`. The kernel checks IDs, physical power, reference and service applicability, and counts the components in the project summary. An `unknown` measurement boundary produces a warning about possible double counting. The legacy TypeScript calculators stop for embedded heat pumps with these records because they do not account for them. Rated power does not imply run hours, seasonal energy or a normative double-counting decision; no auxiliary component is used in BENG yet. Misspelled fields inside components are rejected.

The optional `systemLinks` array records equipment relationships. Each link requires a unique `id`, `role` (`backup_generator`, `upstream_heat_pump`, `shared_source`, or `source_ventilation`), `targetKind` (`heat_pump`, `heating_system`, `hot_water_system`, or `ventilation_system`), `targetId`, and `evidenceReference`. The project audit checks that targets exist and upstream heat-pump links do not form cycles. Upstream and shared-source roles must target a heat pump. A `source_ventilation` link requires an `exhaust_air` source and an existing ventilation-system target; a missing link produces a warning. This is a topology record only: it does not assign operating priority, dispatch hours, ventilation flow, source heat, useful heat, fuel use, or a normative hybrid/cascade route. Embedded links stop the legacy indicative calculator so it cannot silently ignore them.

## MCP server

The `compare_direct_diagnostic` tool accepts the same `{ "case": { ... } }` as the HTTP route and returns the four metric differences. A malformed or invalid case is a tool error. A passing comparison is diagnostic only.

The `mcp` binary runs over stdio. Configure an MCP client to launch the binary with no arguments. It offers `get_capabilities`, `validate_project`, `calculate_beng`, `audit_reference_case`, `diagnose_direct_transmission`, `diagnose_monthly_direct`, `diagnose_unheated_transmission`, `calculate_monthly_demand`, `calculate_space_heating_chain`, `calculate_building_performance`, `calculate_project_performance`, `diagnose_bacs_draft`, `diagnose_indicators_draft`, `diagnose_forfait_heat_pump_draft`, `diagnose_gas_heat_pump_forfait_draft`, `diagnose_gas_heat_pump_aux_draft`, `diagnose_gas_heat_pump_monthly_draft`, `diagnose_gas_heat_pump_chain_draft`, `diagnose_forfait_heat_pump_monthly_draft`, `diagnose_generator_dispatch_draft`, `diagnose_boiler_forfait_draft`, `diagnose_boiler_forfait_monthly_draft`, `diagnose_hybrid_heat_pump_monthly_draft`, `diagnose_heating_aux_draft`, `diagnose_heating_aux_measured_draft`, and `compare_direct_diagnostic`, and `compare_gas_heat_pump_chain_diagnostic`. The project tools accept a `project` object with the same shape as the HTTP API. Tool errors contain JSON text with the same `error` codes as HTTP (`invalid_project_shape`, `invalid_project_input`, `calculation_unavailable`); the last also includes capabilities. `calculate_beng` returns a tool error while calculation is unavailable. `audit_reference_case` accepts `{ "case": { ... } }` with the same manifest shape as the HTTP route; `manifestComplete` checks required fields only, while `referenceVerified` and `calculationAvailable` remain false. The diagnostic tools accept `{ "input": { ... } }` and report a diagnostic value or an input/tool error. Their fields and limitations are documented in `docs/nta8800-directe-transmissie.md`, `docs/nta8800-maandtransmissie.md`, `docs/nta8800-onverwarmde-transmissie.md`, `docs/nta8800-maandbehoefte.md`, `docs/nta8800-verwarmingsketen.md`, `docs/nta8800-energieprestatie-keten.md`, `docs/nta8800-bacs-conceptdiagnose.md`, `docs/nta8800-indicatoren-conceptdiagnose.md`, `docs/nta8800-warmtepomp-hulpenergie-concept.md`, `docs/nta8800-warmtepomp-forfait-cop-concept.md`, `docs/nta8800-warmtepomp-maandinvoer-concept.md`, `docs/nta8800-gaswarmtepomp-hulpenergie-concept.md`, `docs/nta8800-gaswarmtepomp-maandtermen-concept.md`, `docs/nta8800-gaswarmtepomp-gekoppelde-conceptketen.md`, and `docs/nta8800-referentieprotocol.md`.

## Scope

The target version is NTA 8800:2025+C1:2026. The current validation is an early boundary for the Rust kernel, not a full NTA 8800 input audit. Extend the kernel with norm-defined data, algorithms and independently verified reference cases before enabling BENG output or an energy label.

A separate `diagnose_declared_heating_table` MCP tool, HTTP endpoint and desktop command interpolate supplied generation-efficiency, preferred-fraction and auxiliary-electricity table values along gross heat demand and design supply temperature. Both axes must be strictly increasing and the query must remain inside the supplied grid. The response includes the source, selected table scope, bracketing coordinates and interpolation weights. The caller chooses the applicable product and table; no product-match, WLE class, current-edition applicability, annual building balance or BENG is inferred. Four-point excerpts from [BCRG 20250005GK](https://mijn.bcrg.nl/media/documents/2025/GK/20250005GK.pdf) and [BCRG 20260143GG](https://mijn.bcrg.nl/media/documents/2026/GG/20260143GG.pdf) are documented in `docs/nta8800-ruimteverwarming-verklaringstabel.md`.

Classified heat pumps may store `declaredOperatingLimits` for product-specific minimum operating COP and/or maximum supply temperature, with declaration norm edition and source. Validation requires a controlled declaration and finite positive values. The project audit warns that no verified dispatch or backup energy route exists. [BCRG 20240234GK](https://mijn.bcrg.nl/media/documents/2024/GK/20240234GK.pdf) supplies a historical-edition hybrid input example; see `docs/nta8800-hybride-afschakelgrenzen.md`.

An individual electric heat pump may also store `forfaitHeatPumpDraft` with the selected consultation table scope, declared thermal capacity and its evidence, individual/collective status, source class, declared source temperature and evidence for groundwater/collective classes, sink, design supply temperature, correction factor and evidence references. For a collective source at 20 °C or above without a quality-declaration reference, the lookup selects the groundwater-below-15 °C table row and reports `selectedSource` and `sourceFallbackApplied`; residential input then needs an explicit source correction. An explicit `ground_or_groundwater_unknown` class uses the ground row when the type or temperature is unknown; the response includes `sourceFallbackReason`. Declaration authenticity and source classification are not independently checked. `rowVariant=table_9_28_high_efficiency` additionally requires the source-specific NEN-EN 14511-2:2022 test points, each strictly above its table 9.28 threshold, with a product and test-report reference. `/validate` checks this input against the generator and building function, and warns that the table route is unverified; test-report authenticity is not checked. The lookup response is a draft diagnostic; neither the stored input nor its COP enables `/calculate` or a label.

A gas-engine or gas-absorption hydronic heat pump may store `gasHeatPumpForfaitDraft` with a table-9.27/9.29 application, declared capacity, source, design supply temperature and evidence references. The 9.27 residential route requires a collective building installation at most 25 kW; ground and groundwater additionally require a supplied `csource` and evidence. The ambiguous 9.29 collective route at most 25 kW is rejected. `/validate` checks the stored classification against the generator ID, drive, source, sink and building function. It reports the input as unverified and keeps `calculationAvailable=false`; it does not derive gas use or auxiliaries. See `docs/nta8800-gaswarmtepomp-forfait-concept.md` for the public-draft scope and unresolved table 9.27/9.29 overlap.

`compare_reference_case` is also available over MCP with `{ "case": { ... } }`. It compares allowlisted BENG/TOjuli, annual energy/emissions and per-service/per-carrier month or annual output paths against an unverified Rust project calculation; see `docs/nta8800-referentieprotocol.md` for exact paths and units. A numeric match does not validate the supplied source or tolerance and never changes `referenceVerified=false` or `attestStatus=unattested`.
